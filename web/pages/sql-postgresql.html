TECHNICAL GUIDES

Mechanics, tradeoffs and practice.

These are CODARIS editorial explanations. Occupational examples describe engineering responsibilities, not measured demographic shares.

Tables, keys and constraints

Technical model

A relational schema models entities and relationships using tables, primary keys, foreign keys and constraints. Constraints protect durable rules regardless of which application path performs a write. Nullability is part of the model, not only a UI choice.

Failure modes and decisions

Do not rely solely on checking for duplicates before inserting: concurrent requests can both pass that check. Express uniqueness in the database and handle its outcome.

Practice task

Create a saved-item table that permits one URL per member and rejects an empty title.

CREATE TABLE saved_item (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  member_id bigint NOT NULL,
  url text NOT NULL,
  title text NOT NULL CHECK (length(title) > 0),
  UNIQUE (member_id, url)
);

Filtering, joins and missing values

Technical model

A query describes the result needed; the planner chooses an execution strategy. Joins combine related rows, and outer joins preserve unmatched rows when that is part of the requirement. NULL represents missing or unknown information and changes comparison behavior.

Failure modes and decisions

A filter on the nullable side of an outer join can unintentionally remove unmatched rows. Use IS NULL for null tests and decide how aggregates should treat missing data.

Practice task

Write a query for members with no saved items and explain why an inner join cannot return them.

SELECT m.id
FROM member AS m
LEFT JOIN saved_item AS s ON s.member_id = m.id
WHERE s.id IS NULL;
-- Assumes a separate member table with primary key id.

Transactions and rollback

Technical model

A transaction groups changes into a unit that commits or rolls back. This protects operations whose intermediate states should not become durable. Error handling must end or recover the transaction correctly before reusing a connection.

Failure modes and decisions

Transaction boundaries that are too broad hold resources unnecessarily. A database transaction cannot automatically roll back an email already sent through an external service.

Practice task

Insert two related records, deliberately fail the second operation and verify that rollback leaves neither record.

BEGIN;
INSERT INTO saved_item (member_id, url, title)
VALUES (1, 'https://example.test/article', 'Example');
ROLLBACK;
-- The inserted row must not remain.

https://www.postgresql.org/docs/current/tutorial-transactions.html ↗

Concurrency and isolation

Technical model

Concurrent transactions may observe changing data according to the isolation level and operation. Locks, constraints and serialization failures are tools and outcomes to design for, not exceptional details to ignore.

Failure modes and decisions

A read followed by a write can race with another transaction. Keep invariants enforceable, acquire locks deliberately when needed and retry only operations whose semantics permit it.

Practice task

Use two database sessions to attempt the same unique insert and record the result seen by each.

Session A: BEGIN; insert unique item; keep transaction open
Session B: attempt same unique item
Session A: COMMIT
Observe B: uniqueness enforcement, not two durable duplicates

Indexes and EXPLAIN

Technical model

Indexes trade storage and write work for alternate read access paths. EXPLAIN describes a plan; EXPLAIN ANALYZE executes the statement and reports actual observations. Compare estimates with measured behavior using representative data.

Failure modes and decisions

Do not run EXPLAIN ANALYZE on a modifying statement assuming it is read-only. An index can be unused because a scan is cheaper, statistics differ or the query does not match the expected pattern.

Practice task

Load a representative dataset and compare plans for a member-filtered lookup before and after an appropriate index.

EXPLAIN
SELECT id, title FROM saved_item
WHERE member_id = 42
ORDER BY id
LIMIT 20;

https://www.postgresql.org/docs/current/using-explain.html ↗

Parameterized access and operations

Technical model

Parameterized APIs keep values separate from SQL syntax. The backend owns connection credentials and query execution. Operational correctness also requires bounded connection use, migrations and tested recovery, not only a valid SELECT statement.

Failure modes and decisions

Parameters do not stand in for arbitrary identifiers. If table or column choices vary, select from a controlled allowlist rather than concatenating untrusted text. Always check query results and release handles.

Practice task

Describe the ownership of a libpq connection and result object through success and error paths.

const char *values[] = {member_id_text};
PGresult *result = PQexecParams(conn,
  "SELECT id, title FROM saved_item WHERE member_id = $1",
  1, NULL, values, NULL, NULL, 0);
/* Check result and status; copy needed values; PQclear(result). */

APPLY WHAT YOU LEARN

Build and verify.

Build a reading-list schema with users and saved items. Add a uniqueness rule, write a join and aggregation, test rollback, inspect a query plan and document a restore procedure.

Evidence to bring to a review

  • A precise description of the behavior and its boundaries.
  • Tests or observations covering success, invalid input and dependency failure.
  • A short explanation of one tradeoff and a known limitation.
  • Instructions that let another developer reproduce the result.

Examples illustrate individual ideas and are not a complete production application. Run experiments in a disposable environment and adapt them to the documented versions of your tools.
