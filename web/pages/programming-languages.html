01 / ORIENTATION

A language is a set of tradeoffs.

Choose by the problem: deployment target, memory model, libraries, team knowledge and operational constraints. A popularity rank cannot tell you whether a language fits your system.

This library preserves the supplied research pack dated 23 September 2026. Its 674-entry boundary covers notable current and historical programming languages and executable domain-specific languages—not every language ever created.

GitHub activity, survey use and search-interest ratings measure different things. The imported numerical snapshots have not all been independently revalidated. Technical guides are separate CODARIS editorial explanations; occupational examples are not measured demographic shares.

02 / ENGINEERING FOUNDATIONS

What changes between languages?

Type systems & validation

Static checking examines a program before execution; dynamic checks happen while it runs. Inference can reduce explicit annotations without removing static types. Neither approach validates an untrusted network message automatically. Model absent values, distinguish units, and check data at system boundaries.

Execution: native code, virtual machines & WebAssembly

Ahead-of-time compilers produce code before execution; just-in-time compilers optimize during execution. Interpreters execute a representation of the program. A language can have multiple implementations. WebAssembly is a portable instruction format and compilation target, not a replacement for every host API.

CODARIS compiles C17 to WebAssembly for browser application logic. Browser glue supplies DOM and platform access. Native C handles the backend.

Memory, ownership & resource lifetime

Manual management puts allocation and release under programmer control. Garbage collection reclaims unreachable memory. Ownership systems constrain who can access or release resources. Files, sockets and database handles still require explicit lifetime decisions; a memory-safe language does not eliminate resource leaks.

Concurrency & failure

Threads, async tasks and actors offer different ways to organize overlapping work. Concurrency does not guarantee parallel execution. Define cancellation, deadlines, queue limits, shared-state ownership and retry behavior before scaling a service.

Paradigms & domain-specific languages

Procedural code organizes steps; object-oriented code groups behavior around objects; functional code emphasizes composition and values; declarative code describes desired results. Many languages combine these. A domain-specific language narrows its vocabulary to a problem area, such as querying relational data with SQL.

How to evaluate a language for a project
  1. Write down the target platform, latency and memory limits.
  2. Check library availability and maintenance for your actual workload.
  3. Prototype the hardest integration and failure paths.
  4. Measure representative performance rather than comparing toy loops.
  5. Document build reproducibility, debugging and deployment ownership.

Roles, mechanics and practical exercises.

CSystems / embedded

Role & typical users

Systems engineers, firmware developers and library maintainers use C to work close to operating-system and hardware interfaces.

Technical model

Static types, explicit pointers and manual resource lifetimes. Implementations commonly compile ahead of time to native code. The language does not automatically enforce bounds or ownership.

Engineering considerations

Reason about allocation failure, integer overflow, bounds and cleanup on every exit. Use compiler warnings, sanitizers and parameterized interfaces. CODARIS uses C17 for native code and C compiled to WebAssembly in the browser.

Try building

Build a bounded text parser; test empty, oversized and malformed input.

C++Systems / performance

Role & typical users

Engine, graphics and native application developers use C++ when they need low-level control alongside reusable abstractions.

Technical model

Static typing, templates, deterministic destruction and RAII support resource ownership. Native code can use object-oriented, generic and functional techniques.

Engineering considerations

Prefer explicit ownership and standard containers. Lifetime bugs, undefined behavior and complex build interfaces still require careful review.

Try building

Implement a file-processing tool with RAII and unit tests for failure paths.

Primary documentation ↗

RustSystems / reliability

Role & typical users

Systems and infrastructure developers use Rust for components where memory safety and predictable resource ownership matter.

Technical model

Ownership, borrowing and lifetimes constrain aliasing in safe code. Traits and enums model interfaces and state; Result and Option make failure and absence explicit.

Engineering considerations

Safe Rust prevents many memory errors, but unsafe blocks and foreign interfaces need separate auditing. Concurrency still requires sound design.

Try building

Write a command-line parser that returns structured errors without panicking.

GoServices / infrastructure

Role & typical users

Backend and platform developers use Go for network services, command-line tools and operational software.

Technical model

Static types, interfaces, garbage collection, goroutines and channels support compact concurrent programs. Packages and modules organize builds.

Engineering considerations

Design cancellation, timeouts and ownership of shared state. A goroutine is lightweight but can still leak when blocked indefinitely.

Try building

Build a small HTTP service with bounded requests, cancellation and graceful shutdown.

PythonAutomation / data

Role & typical users

Automation developers, analysts and backend engineers use Python for scripts, data workflows and services.

Technical model

Dynamic types, high-level collections and modules favor rapid iteration. Type annotations help tools but do not enforce runtime validation by themselves.

Engineering considerations

Keep environments reproducible, validate boundary data and profile before optimizing. Native extensions can accelerate work but introduce their own failure modes.

Try building

Parse a CSV, validate rows and produce a reproducible summary with tests.

JavaScriptWeb / applications

Role & typical users

Browser and server developers use JavaScript for interactive interfaces and event-driven applications.

Technical model

Dynamic typing, lexical closures, prototypes, promises and modules. The host supplies APIs such as the DOM or server I/O; these are not identical across runtimes.

Engineering considerations

Understand coercion and asynchronous error handling. Do not block the event loop with expensive synchronous work; validate all external input.

Try building

Build an accessible interactive list with loading, empty and error states.

Primary documentation ↗

TypeScriptWeb / typed applications

Role & typical users

Application teams use TypeScript to describe JavaScript interfaces and catch many mistakes before execution.

Technical model

Structural typing, unions, generics and control-flow narrowing add static analysis. Most type information is erased when emitting JavaScript.

Engineering considerations

Types do not validate JSON at runtime. Treat network and storage values as untrusted until checked; avoid hiding uncertainty behind any.

Try building

Model a request as loading, success or failure with a discriminated union.

Primary documentation ↗

JavaServices / JVM

Role & typical users

Backend and application developers use Java within the JVM ecosystem and its extensive libraries and tools.

Technical model

Static types, classes, interfaces, generics and exceptions. JVM implementations manage memory and commonly use just-in-time compilation.

Engineering considerations

Budget heap use, close external resources deterministically and choose concurrency abstractions deliberately. Garbage collection does not close every resource.

Try building

Build a small service layer with typed inputs and tests around exception handling.

Primary documentation ↗

C#Applications / .NET

Role & typical users

Service, desktop and game-tool developers use C# with the .NET ecosystem.

Technical model

Static typing with generics, pattern matching, LINQ and async/await. Managed memory reduces manual allocation work; IDisposable handles many external resources.

Engineering considerations

Await asynchronous work, propagate cancellation and dispose resources. Nullable annotations help analysis but are not a substitute for boundary validation.

Try building

Write an asynchronous file-processing tool with cancellation and explicit errors.

RubyWeb / scripting

Role & typical users

Web application developers and automation authors use Ruby for expressive object-oriented programs and internal tools.

Technical model

Dynamic typing, objects, blocks and mixins support compact APIs. Ruby on Rails supplies a separate web framework around the language.

Engineering considerations

Metaprogramming can obscure control flow. Keep behavior discoverable, test public interfaces and monitor dependencies.

Try building

Create a small command-line report using Enumerable and tests.

RStatistics / research

Role & typical users

Statisticians, researchers and analysts use R for modelling, statistical computing and graphics.

Technical model

Vectors, data structures and an extensible package ecosystem support analysis. Missing values and vectorized operations are central concepts.

Engineering considerations

Record package versions, random seeds and data provenance. Inspect missingness and assumptions before presenting a statistical result.

Try building

Create a reproducible report that separates raw data, transformations and interpretation.

Primary documentation ↗

SQLData / relational systems

Role & typical users

Application developers, analysts and database engineers use SQL to define, query and modify relational data.

Technical model

Declarative queries describe results; the database planner selects an execution strategy. Constraints, transactions and indexes shape correctness and performance.

Engineering considerations

Dialects differ. Use parameter binding for values, review query plans and understand transaction isolation. NULL introduces three-valued logic.

Try building

Design a reading-list schema with foreign keys and a parameterized query.

Primary documentation ↗

LuaEmbedding / scripting

Role & typical users

Host-application and game developers use Lua to make software scriptable without replacing its native core.

Technical model

A small embeddable language with dynamic types, tables, functions and coroutines. A C API connects the interpreter to its host.

Engineering considerations

The host decides available capabilities. Sandbox untrusted scripts deliberately and control resource consumption and exposed APIs.

Try building

Embed a configuration script in a small host and validate the returned values.

Primary documentation ↗

ErlangDistributed / concurrent

Role & typical users

Developers of concurrent services use Erlang processes and message passing to isolate work.

Technical model

Lightweight processes communicate through mailboxes. Links and monitors support failure observation; OTP adds reusable supervision and service patterns.

Engineering considerations

Plan overload behavior, mailbox growth and recovery. Distribution does not remove partial failure or network partitions.

Try building

Model two communicating processes and test what happens when one stops.

Primary documentation ↗

HaskellFunctional / typed modelling

Role & typical users

Developers and researchers use Haskell to express transformations and domain models with strong static types.

Technical model

Pure functions, algebraic data types, type inference and non-strict evaluation are central. Effects are represented explicitly in typed interfaces.

Engineering considerations

Laziness changes when work and allocation happen. Watch space use, make effects visible and keep abstractions understandable to the team.

Try building

Model a small domain with sum types and test pure transformations.

READ THIS FIRST There is no honest single 'usage %' for every programming language. This workbook keeps separate metrics: GitHub public-code activity, Stack Overflow self-reported usage, and TIOBE search/popularity rating. Country data and gender data have different coverage and should not be inferred where absent.

Coverage note — Meaning

Catalogue — Notable current/historical executable languages and DSLs, under 1,000 entries.

Country — GitHub supports language-by-economy counts; this pack includes methodology plus a verified Bangladesh example and SO respondent geography.

Gender — Per-language male/female percentages are intentionally not fabricated. JetBrains 2025 raw survey is a suitable source for future cross-tabs.

Gender data notes · workbook notes

Question — What is verified · What is NOT verified · CODARIS recommendation

Can we publish male/female % for every language? — JetBrains 2025 includes gender and language variables and offers anonymized raw survey data. · No reliable published per-language male/female percentages were verified in this research pass. · Do not invent values. Cross-tab the raw survey, publish sample sizes, include non-binary/prefer-not-to-say categories, and label it as survey data.

Can we call survey gender shares 'all programmers'? — No. Surveys describe their respondents, subject to sampling/weighting choices. · They are not a census of the global developer population. · Use wording such as 'among respondents to the 2025 JetBrains Developer Ecosystem Survey'.

Should CODARIS force binary gender categories? — The cited JetBrains report includes Male, Female, Prefer not to say, and Non-binary/genderqueer/gender non-conforming. · A binary-only table would discard reported categories. · Preserve the source categories and allow 'unknown / not reported' rather than guessing.

Methodology · workbook notes

Topic — Rule used in this pack · Why it matters

Catalogue scope — Uses the English Wikipedia index of notable programming languages. It is not a claim to contain every language ever created. · Thousands of experimental, esoteric, dialect and internal languages exist; a bounded educational catalogue needs a declared scope.

HTML/CSS — Included in Stack Overflow usage rankings because that survey category explicitly includes programming, scripting and markup languages, but not added to the core programming-language catalogue because the catalogue source excludes markup languages. · Prevents mixing incompatible taxonomies.

GitHub metric — Unique developers in an economy making at least one git push to a repository containing a language during a quarter. · Measures public GitHub coding activity, not total programmers, jobs, lines of code, or private work.

GitHub geography — Economy based on GitHub methodology; data is quarterly and public-only; low-count economies may be withheld. · Country comparisons can be incomplete and should not be treated as census estimates.

Stack Overflow usage — Self-reported extensive development work in the past year; multiple languages can be selected. · Percentages overlap and do not add to 100.

Stack Overflow countries — Where survey respondents live. · Useful for sample composition only, not for ranking the total developer population by country.

TIOBE — Popularity index derived from search/activity signals around skilled engineers, courses, vendors and web sources. · It is not a direct measure of actual language usage.

Gender — No per-language percentages are populated unless a source directly supports them. · Avoids false precision and demographic fabrication.

Ranking — No composite 'best language' score is created. · Different sources measure different constructs; combining them without a defensible model would be misleading.
