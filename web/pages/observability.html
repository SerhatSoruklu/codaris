Observability, Logging & Monitoring.

Observability uses evidence from a running system to investigate behavior. Metrics, logs, traces and profiles answer different questions. Instrumentation and collection are separate from storage, querying and visualization; a dashboard alone is not a reliability strategy.

TECHNICAL GUIDES

Mechanics, tradeoffs and practice.

These are CODARIS editorial explanations. Occupational examples describe engineering responsibilities, not measured demographic shares.

Metrics and useful dimensions

Technical model

Metrics aggregate measurements such as counts, durations and resource use. Labels divide a measurement into dimensions. Counters and histograms support different analyses; units and aggregation semantics should be explicit.

Failure modes and decisions

Unbounded labels such as request IDs or raw user input can create excessive cardinality. Choose dimensions that answer operational questions without storing a time series for every unique event.

Practice task

Design request-rate and latency metrics for an API using bounded labels. Explain which labels you deliberately exclude.

https://prometheus.io/docs/practices/naming/ ↗

Structured logs and sensitive data

Technical model

Logs record events with context. Structured fields support correlation and filtering better than inconsistent prose alone. Severity levels should reflect operational meaning rather than simply how much text a developer wants to see.

Failure modes and decisions

Do not log credentials, session tokens or unnecessary personal data. Bound payload size and retention, and preserve useful identifiers without making every message sensitive.

Practice task

Define a failed-request log event with timestamp, operation, status and correlation ID; remove fields not needed for diagnosis.

https://opentelemetry.io/docs/concepts/signals/logs/ ↗

Distributed traces and context propagation

Technical model

A trace groups spans representing related work across component boundaries. Parent-child relationships and timing reveal where time was spent. Propagated context connects operations that otherwise look like unrelated requests.

Failure modes and decisions

Sampling affects what evidence exists. Avoid treating a sampled trace as a complete record of all traffic, and do not trust arbitrary inbound trace fields as authorization or identity.

Practice task

Trace a request through an API, queue and worker. Explain where asynchronous work creates a new span relationship.

https://opentelemetry.io/docs/concepts/signals/traces/ ↗

Collection pipelines and telemetry backends

Technical model

Instrumentation produces signals; collectors can receive, process and export them; backends store and query them. OpenTelemetry is an instrumentation and interoperability ecosystem, not a single storage database.

Failure modes and decisions

Telemetry pipelines can fail or saturate. Set bounded queues, understand dropping behavior and make collection failures observable without creating a feedback loop of logs.

Practice task

Draw a pipeline for traces and metrics with one collector failure. Explain what is buffered, dropped or retried.

https://opentelemetry.io/docs/collector/ ↗

Service objectives and actionable alerts

Technical model

An objective describes an acceptable level of user-visible service over a period. Indicators should measure that experience. Alerts should lead to a meaningful response when the objective is threatened or an urgent condition occurs.

Failure modes and decisions

Alerting on every internal fluctuation creates noise. Distinguish diagnostic dashboards from paging conditions, and attach ownership and a runbook to each actionable alert.

Practice task

Define availability and latency indicators for a login endpoint, then write an alert with a clear first response.

https://sre.google/sre-book/service-level-objectives/ ↗

Profiles and incident investigation

Technical model

Profiles sample or measure where CPU time, allocations or other resources are spent. They complement traces by explaining internal resource consumption. A useful incident investigation compares evidence against a hypothesis and a timeline.

Failure modes and decisions

Do not optimize from an unrepresentative profile. Match the binary and workload, account for measurement overhead and verify improvement against the original symptom.

Practice task

Given high latency with low CPU, list evidence that distinguishes lock contention, network waits and a saturated database.

https://www.brendangregg.com/flamegraphs.html ↗
