Roles and responsibilities.

TECHNICAL GUIDES

Mechanics, tradeoffs and practice.

These are CODARIS editorial explanations. Occupational examples describe engineering responsibilities, not measured demographic shares.

Semantic HTML and document structure

Technical model

Headings, landmarks, links, buttons and form controls carry meaning beyond their appearance. Use the element that matches the action: links navigate, buttons perform actions, and labels identify inputs. This supports keyboards and assistive technologies.

Failure modes and decisions

Clickable generic elements need extra behavior and semantics that native controls already provide. Keep heading order and accessible names meaningful rather than styling every title identically.

Practice task

Build a topic card with a heading, description and named navigation link. Test it using only the keyboard.

<article>
  <h2>Databases</h2>
  <p>Explore models, transactions and recovery.</p>
  <a href="/databases/">View database topic</a>
</article>

Responsive layout and readable content

Technical model

CSS layout defines relationships between elements under changing space constraints. Grid and flex layouts can adapt without fixed pixel assumptions, while sensible line lengths and wrapping preserve readability.

Failure modes and decisions

A desktop screenshot does not establish mobile usability. Test long labels, large text, narrow screens and wide tables; local scrolling should not force the entire page wider than the viewport.

Practice task

Make a three-column topic grid collapse to one column and verify that a long title does not overflow.

.topics {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(min(100%, 18rem), 1fr));
  gap: 1rem;
}

https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/CSS_layout/Responsive_Design ↗

Forms and useful feedback

Technical model

A form needs labels, constraints, instructions and feedback that survives failure. Associate errors with the affected control and explain how to recover. Preserve valid input where possible instead of forcing users to restart.

Failure modes and decisions

Client validation can be bypassed and must be repeated at the trusted boundary. Do not use placeholder text as the only label or rely only on color to communicate an error.

Practice task

Create a required display-name input with an inline error and a status region for submission results.

<label for="display-name">Display name</label>
<input id="display-name" aria-describedby="name-error" required>
<p id="name-error">Enter a display name.</p>
<p role="status" aria-live="polite"></p>

https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms ↗

HTTP requests and representations

Technical model

HTTP messages carry methods, targets, status codes, headers and optional bodies. A response body is a representation whose type and caching behavior should be explicit. Network success and application success are different layers.

Failure modes and decisions

A successful connection can still return an application error. Handle timeouts, malformed responses and unexpected status codes deliberately instead of assuming every response contains the expected JSON.

Practice task

Describe the client behavior for 200, 400, 401, 404 and 503 responses without exposing internal server details.

GET /topics HTTP/1.1
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: public, max-age=60

https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview ↗

Browser trust and safe rendering

Technical model

Browser code executes in a user-controlled environment. Server authorization protects data, while safe DOM operations prevent untrusted text from becoming executable markup. Origin and content-security policies add boundaries but do not replace correct rendering.

Failure modes and decisions

Do not interpolate arbitrary text into HTML or expose server credentials to client code. Treat URL handling, script loading and third-party code as explicit trust decisions.

Practice task

Render a user message containing angle brackets as literal text and verify that no new element or event handler is created.

const message = document.createElement("p");
message.textContent = userSuppliedText;
container.append(message);

https://developer.mozilla.org/en-US/docs/Web/API/Node/textContent ↗

Progressive enhancement and performance

Technical model

Start from usable content and add interaction where it improves a workflow. Loading, failure and reduced-capability states should remain understandable. Measure transferred bytes, main-thread work and visible responsiveness separately.

Failure modes and decisions

An animation or client bundle can improve appearance while delaying useful interaction. Respect reduced motion and avoid making static reading depend on a successful runtime download.

Practice task

Disable JavaScript on a documentation page and list which capabilities still work. Add a fallback for any essential task that disappears.

Baseline: readable content + native links + disclosures
Enhancement: search + local progress + richer interaction
Failure: explain missing enhancement without hiding the content

https://developer.mozilla.org/en-US/docs/Glossary/Progressive_Enhancement ↗

APPLY WHAT YOU LEARN

Build and verify.

Build a responsive documentation page with semantic navigation, a labelled form and a progressively enhanced search. Test narrow screens, keyboard use, script failure and safe rendering of user text.

Evidence to bring to a review

  • A precise description of the behavior and its boundaries.
  • Tests or observations covering success, invalid input and dependency failure.
  • A short explanation of one tradeoff and a known limitation.
  • Instructions that let another developer reproduce the result.

Examples illustrate individual ideas and are not a complete production application. Run experiments in a disposable environment and adapt them to the documented versions of your tools.
