Testing & QA.

Testing collects evidence about behavior under selected conditions. Quality work combines focused tests, boundary checks, realistic integration paths and useful failure diagnosis. A tool catalogue is not a test strategy by itself.

ORIENTATION

Roles and responsibilities.

Developers test logic and interfaces; QA engineers investigate workflows and risks; reliability teams test load, recovery and operational assumptions.

How the pieces relate

Requirement → observable behavior → test setup → assertion
                      failure → diagnosis → regression protection

TECHNICAL GUIDES

Mechanics, tradeoffs and practice.

These are CODARIS editorial explanations. Occupational examples describe engineering responsibilities, not measured demographic shares.

Unit tests and meaningful boundaries

Technical model

A unit test exercises a small behavior with controlled inputs and a clear observable result. Useful boundaries include empty input, invalid input, minimum and maximum values, and combinations that challenge an invariant.

Failure modes and decisions

Avoid asserting private implementation details unless they are part of the contract. A test that repeats the implementation can reproduce its mistake rather than detect it.

Practice task

Write tests for a parser using valid, empty, truncated and oversized inputs. State which invariant each test protects.

https://docs.pytest.org/en/stable/how-to/assert.html ↗

Integration and contract tests

Technical model

Integration tests exercise components together, such as a service and database. Contract tests verify that producers and consumers agree on data shapes and behavior. Both should make version and environment assumptions explicit.

Failure modes and decisions

Mocks can hide incompatible serialization, transaction behavior or permissions. Use realistic boundaries where those interactions are the risk. Ensure test data is isolated and cleanup is deterministic.

Practice task

Test a service query against a disposable database and verify both results and constraint failures.

https://docs.pact.io/ ↗

Browser and accessibility flows

Technical model

End-to-end browser checks observe user-visible behavior across navigation, input and rendering. Semantic locators encourage controls with names and roles. Include keyboard operation and empty, loading and failure states.

Failure modes and decisions

Fixed sleeps and brittle element positions produce flaky tests. Wait for observable state, isolate test accounts and verify outcomes rather than only clicks.

Practice task

Test registration validation and keyboard focus after an error. Simulate a failed response and assert a useful message.

https://playwright.dev/docs/best-practices ↗

Property-based and fuzz testing

Technical model

Property-based testing explores many generated inputs against invariants. Fuzzing searches input space for crashes or unwanted behavior. These methods complement concrete examples by exposing cases a human may not enumerate.

Failure modes and decisions

A weak property can pass while the program is wrong. Bound resources, preserve failing seeds and reduce failures to minimal reproductions that can become regression tests.

Practice task

For an encoder/decoder pair, test round trips within a documented domain and keep malformed inputs as separate negative cases.

https://hypothesis.readthedocs.io/en/latest/ ↗

Performance and load experiments

Technical model

Performance tests need a representative workload, environment and measurement method. Report latency distributions, throughput, resource usage and error rate together. Warmup, contention and data size can change results substantially.

Failure modes and decisions

Do not infer capacity from a single successful request or average latency alone. Watch queue growth and recovery after overload; a saturated system can hide failures through retries.

Practice task

Compare steady traffic with a short burst and explain the difference between median and tail latency.

https://grafana.com/docs/k6/latest/testing-guides/ ↗

Coverage, mutation and maintenance

Technical model

Coverage tells you which code was executed, not whether assertions could detect a defect. Mutation testing changes behavior to investigate test sensitivity. A maintained suite gives fast, actionable feedback for real change risks.

Failure modes and decisions

More tests are not automatically better. Remove redundant checks, investigate flakiness and keep expensive scenarios focused on risks that cheaper tests cannot cover.

Practice task

Find a condition covered by a test, invert it temporarily in a scratch branch and confirm whether the test notices.

https://pitest.org/ ↗
