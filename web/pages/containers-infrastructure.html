Containers, Orchestration & Infrastructure.

Containers package processes and dependencies; orchestrators schedule and reconcile workloads; infrastructure tools manage external resources. These layers interact but have different state and failure models. Keep application health separate from the fact that a container is running.

TECHNICAL GUIDES

Mechanics, tradeoffs and practice.

These are CODARIS editorial explanations. Occupational examples describe engineering responsibilities, not measured demographic shares.

Images, layers and process isolation

Technical model

An image is a packaged filesystem and execution configuration. A container runs a process using isolation mechanisms supplied by the host. Image layers aid distribution and reuse; they do not by themselves establish a trusted execution boundary.

Failure modes and decisions

Avoid embedding secrets in any layer, even if a later layer deletes them. Pin important image inputs and run with only required privileges and mounts.

Practice task

Inspect an image history and list its entry point, user, writable paths and external configuration requirements.

https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-an-image/ ↗

Scheduling and resource requests

Technical model

An orchestrator places workloads based on resource requests, constraints and available capacity. Controllers reconcile desired state after changes and failures. Restarting a process is one recovery action, not proof that the underlying fault is fixed.

Failure modes and decisions

Incorrect requests can distort placement, while aggressive limits can terminate work unexpectedly. Plan disruption budgets, graceful shutdown and overload behavior alongside scaling.

Practice task

Design resource requests for a CPU-bound worker and an I/O-bound service, then explain how you would measure whether they are appropriate.

https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/ ↗

Readiness, liveness and startup

Technical model

Readiness answers whether a workload should receive traffic. Liveness asks whether restarting it may help. Startup checks allow initialization before other health decisions. Distinguishing these prevents a slow dependency from creating a restart storm.

Failure modes and decisions

A health endpoint that always returns success hides failure; one that restarts on every external dependency failure can amplify an outage. Test degraded conditions explicitly.

Practice task

Write three health contracts and describe what happens while the database is temporarily unavailable.

https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/ ↗

Persistent state and configuration

Technical model

Container replacement should not silently destroy authoritative data. Volumes and external stores have independent lifetimes, while configuration and secret delivery define how a workload is parameterized.

Failure modes and decisions

A persistent volume is not a backup. Review access modes, restore procedures, mount permissions and schema compatibility before rolling out an application change.

Practice task

Replace a workload in a disposable environment and verify which data survives. Document how to recover after deleting the backing storage.

https://kubernetes.io/docs/concepts/storage/persistent-volumes/ ↗

Infrastructure as code and drift

Technical model

Infrastructure definitions describe desired resources and relationships. Planning and state tracking help tools compare intent with observed resources. Changes made outside that workflow can create drift and unexpected later operations.

Failure modes and decisions

Review plans before applying them, secure state files and serialize conflicting changes. A successful plan is not proof that application-level behavior will remain correct.

Practice task

Identify how a renamed resource differs from an in-place update and describe the risk of an accidental replacement.

https://developer.hashicorp.com/terraform/intro ↗

Configuration, packaging and supply chains

Technical model

Charts, templates and overlays produce deployment configuration from reusable definitions. Their values influence permissions, networking, image versions and resource limits. Generated manifests are the actual deployment input.

Failure modes and decisions

Review rendered output as well as templates. Keep dependencies and images attributable, and avoid hiding broad privileges inside shared defaults.

Practice task

Render a deployment for two environments and compare only the settings that are supposed to differ.

https://helm.sh/docs/topics/charts/ ↗
