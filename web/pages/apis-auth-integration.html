APIs, Protocols, Auth & Integration.

An API defines a contract across a boundary. Protocols transport messages; schemas describe shapes; identity standards establish authentication or authorization flows; products implement parts of those systems. Keeping these layers separate makes integration easier to reason about.

Roles and responsibilities.

How the pieces relate

                                      → application operation → response

TECHNICAL GUIDES

Mechanics, tradeoffs and practice.

These are CODARIS editorial explanations. Occupational examples describe engineering responsibilities, not measured demographic shares.

HTTP methods and resource contracts

Technical model

HTTP specifies method semantics, status codes and representation metadata. An application contract adds resource meaning, validation rules and error shapes. A documented endpoint should describe both successful and unsuccessful outcomes.

Failure modes and decisions

Do not use a status code alone as a complete error contract. Consider caching, conditional requests and whether a method can be retried safely after a lost response.

Practice task

Design create and read operations for a project resource, including invalid input, missing resources and permission failures.

https://www.rfc-editor.org/rfc/rfc9110.html ↗

Schemas, compatibility and evolution

Technical model

Schemas describe message structures and constraints, while compatibility rules determine whether old and new participants can communicate. Adding a field is not automatically harmless if consumers reject unknown fields or interpret absence differently.

Failure modes and decisions

Avoid changing a field’s meaning without a migration plan. Specify nullability, defaults and version behavior, and test consumers against representative older payloads.

Practice task

Evolve an event with an optional field, then explain how an old consumer and a new consumer handle both versions.

https://spec.openapis.org/oas/latest.html ↗

Authentication versus authorization

Technical model

Authentication establishes an identity claim; authorization decides what that identity may do. OAuth addresses delegated authorization, while OpenID Connect adds identity functionality on top of OAuth. An identity product is an implementation, not the protocol itself.

Failure modes and decisions

A valid token does not grant access to every object. Validate the intended issuer and audience, enforce object-level permissions, and use maintained protocol libraries rather than inventing a flow.

Practice task

For a project API, separate token validation from checking membership of the specific project being requested.

https://openid.net/specs/openid-connect-core-1_0.html ↗

OAuth threat boundaries

Technical model

Redirects, authorization codes, clients and tokens cross multiple trust boundaries. Modern security guidance addresses risks such as code interception, token leakage and misdirected authorization responses. The correct flow depends on the type of client.

Failure modes and decisions

Do not embed confidential-client secrets in browser or mobile applications. Follow current protocol guidance, validate redirect handling and keep tokens out of logs and URLs where they can leak.

Practice task

Draw a browser sign-in flow and mark where code exchange, session creation and API authorization occur.

https://www.rfc-editor.org/rfc/rfc9700.html ↗

Webhooks and long-lived connections

Technical model

A webhook delivers an event through a request initiated by the producer; a WebSocket provides a long-lived bidirectional connection. Both need authentication, resource limits, reconnect behavior and a strategy for missed or repeated messages.

Failure modes and decisions

A live connection does not guarantee application delivery. Verify webhook signatures with maintained implementations and replay protection; make repeated events safe to process.

Practice task

Design a reconnect flow that resumes from a last-seen event ID without silently losing or duplicating visible work.

https://www.rfc-editor.org/rfc/rfc6455.html ↗

Integration reliability and idempotency

Technical model

Integrations fail through timeouts, partial success and incompatible assumptions. A stable operation identifier can help make retries safe. Deadlines, bounded retries and clear ownership limit the blast radius of a failing dependency.

Failure modes and decisions

A timeout is uncertainty, not proof of failure. Avoid retrying irreversible actions blindly, and expose a way to reconcile status after an ambiguous result.

Practice task

Specify an idempotent job-submission endpoint and explain what it returns when the same key is reused with a different payload.

https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/ ↗
