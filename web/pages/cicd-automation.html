ORIENTATION

Roles and responsibilities.

Contributors produce changes; release engineers build and promote artifacts; operators decide rollout, rollback and approval policies.

How the pieces relate

Commit → isolated checks → immutable artifact → promotion
       → staged rollout → health evidence → continue / rollback

TECHNICAL GUIDES

Mechanics, tradeoffs and practice.

These are CODARIS editorial explanations. Occupational examples describe engineering responsibilities, not measured demographic shares.

Events, jobs and dependencies

Technical model

A workflow starts from a defined event and schedules jobs with declared relationships. Jobs may run concurrently, so ordering and data transfer must be explicit. Required checks should correspond to the revision being integrated.

Failure modes and decisions

Do not trust outputs from an unrelated revision or accidentally skip an essential check through a conditional. Identify the difference between a failed job, a cancelled job and a job that never ran.

Practice task

Sketch a pipeline with lint, unit tests, integration tests and packaging; mark which jobs can run independently.

https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows ↗

Runner isolation and untrusted changes

Technical model

A runner executes repository-controlled commands. Pull requests and dependency scripts may be untrusted input, particularly when they can access credentials or persistent runner state. Isolation should match that risk.

Failure modes and decisions

Separate privileged deployment jobs from untrusted validation. Use least-privilege tokens, avoid interpolating untrusted text into shell code and clean or replace workspaces between jobs.

Practice task

Trace which secrets a forked contribution could access in a proposed workflow and remove every unnecessary path.

https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions ↗

Artifacts versus caches

Technical model

An artifact is an output to retain or promote. A cache speeds up recomputation of reusable inputs or intermediates. Their integrity, retention and identity requirements differ, especially across trusted and untrusted jobs.

Failure modes and decisions

Do not treat a mutable cache as the authoritative release. Record checksums, source revision and build inputs for artifacts, and verify what a downstream job downloads.

Practice task

Design an artifact name and manifest that unambiguously identifies the tested build across staging and production.

https://docs.github.com/en/actions/using-workflows/storing-workflow-data-as-artifacts ↗

Deployment strategies and rollback

Technical model

A rollout changes a running population of instances. Rolling, blue/green and canary approaches provide different ways to observe impact and control exposure. Success needs application health evidence, not only process startup.

Failure modes and decisions

A binary rollback may not reverse an incompatible schema migration. Plan backward-compatible changes and define measurable conditions for stopping a rollout.

Practice task

Design a canary experiment with an error-rate threshold and a rollback procedure that includes data compatibility.

https://sre.google/sre-book/release-engineering/ ↗

GitOps reconciliation

Technical model

GitOps controllers compare declared configuration with a running environment and reconcile differences. The repository becomes a desired-state input, while the controller still needs credentials, validation and safe operational behavior.

Failure modes and decisions

Automatic reconciliation can undo emergency manual edits or repeatedly apply a harmful declaration. Document break-glass procedures and ownership of each resource.

Practice task

Explain how an emergency scaling change is reconciled back into version control without being silently overwritten.

https://argo-cd.readthedocs.io/en/stable/ ↗

Release evidence and incident learning

Technical model

A release record connects the change, checks, artifact, deployment and observed outcome. Failed releases are opportunities to improve detection and recovery rather than merely rerun a job until it turns green.

Failure modes and decisions

Blind retries can conceal nondeterminism or repeat an irreversible operation. Make deployment steps idempotent where possible and preserve diagnostic evidence before cleanup.

Practice task

Write a concise release report containing the trigger, exact artifact, failed stage, user impact and recovery action.

https://sre.google/sre-book/postmortem-culture/ ↗
