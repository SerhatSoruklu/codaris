Cloud, Hosting & Serverless.

Cloud architecture distributes responsibility between your team and a provider. Virtual machines, managed platforms, functions, object storage and edge networks expose different control surfaces. Choose from explicit requirements rather than treating every service as equivalent hosting.

TECHNICAL GUIDES

Mechanics, tradeoffs and practice.

These are CODARIS editorial explanations. Occupational examples describe engineering responsibilities, not measured demographic shares.

Compute and the responsibility boundary

Technical model

A virtual machine exposes an operating-system boundary you normally manage. A platform service manages more runtime lifecycle on your behalf. Functions organize work around invocations and provider-defined execution environments.

Failure modes and decisions

Managed does not mean responsibility-free. You still own application permissions, data handling and failure behavior. Document patching, backups and upgrade ownership for each component.

Practice task

Compare one application on a VM, a managed web platform and a function. Assign each operational responsibility to a named owner.

https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html ↗

Regions, zones and data placement

Technical model

Regions and availability zones describe failure and placement domains, but their guarantees vary by service. Placing instances in separate zones can reduce one failure risk while leaving shared dependencies elsewhere.

Failure modes and decisions

Multiple instances are not resilience if they all depend on one unhealthy database or identity service. Cross-region designs also introduce latency, replication and recovery tradeoffs.

Practice task

Draw a dependency map and identify failures that survive losing one compute instance versus an entire zone.

https://docs.aws.amazon.com/whitepapers/latest/aws-overview/global-infrastructure.html ↗

Identity, permissions and secret delivery

Technical model

Cloud identity determines which people and workloads can act on resources. Prefer narrowly scoped workload identities where available and separate development, deployment and runtime permissions. Secrets need a lifecycle, not only a storage location.

Failure modes and decisions

A compromised build runner should not automatically control production data. Rotate credentials, avoid embedding them into images or logs, and review permission changes like application changes.

Practice task

Write a permission matrix for a web service, migration job and backup job. Identify which privileges each should never have.

https://cloud.google.com/iam/docs/overview ↗

Serverless execution and state

Technical model

A function execution environment may be reused but should not be treated as durable storage. External state, retries, concurrent invocations and provider time limits influence application design.

Failure modes and decisions

Repeated delivery can execute a handler more than once. Use idempotency for external effects, cap concurrency to protect dependencies and distinguish timeout from confirmed failure.

Practice task

Design an image-processing function with a stable job key. Explain how retries avoid duplicate billing or notifications.

https://docs.aws.amazon.com/lambda/latest/dg/best-practices.html ↗

Edge networks, caching and origins

Technical model

An edge network can serve cached content or execute work close to users. Cache keys, freshness and invalidation determine which response is reused. The origin remains responsible for content and many authorization decisions.

Failure modes and decisions

Never let a cache mix private responses across users. Review cookies, authorization headers and variation rules before caching dynamic content. Validate behavior during origin failure.

Practice task

Create a caching policy for public documentation and authenticated settings. Explain why their cache keys and retention differ.

https://developers.cloudflare.com/cache/concepts/ ↗

Cost models and recovery drills

Technical model

Compute time, requests, storage, data transfer and managed features can all contribute to cost. Design with representative usage rather than free-tier assumptions, and establish recovery objectives before a failure.

Failure modes and decisions

Autoscaling may amplify an expensive dependency problem. Set budgets and limits, measure unit cost, and rehearse restoring the application with its data and configuration.

Practice task

Estimate cost drivers for a tenfold traffic burst and run a written restoration exercise with an explicit recovery-time target.

https://learn.microsoft.com/en-us/azure/well-architected/ ↗

## Scope

This pack contains **140 catalogue entries** for **Cloud, Hosting & Serverless**.

Separates public cloud providers, CDN/edge networks, application PaaS, frontend hosting, serverless/FaaS, VM hosting and hosting-control platforms. The Stack Overflow 2025 'cloud development' question mixes several of these layers, so source percentages are not treated as cloud market share.

## Research integrity

- Popularity/adoption values are kept tied to their named source, year and denominator/scope.
- Survey percentages are not treated as global market share unless the source explicitly measures market share.
- Country-by-tool and gender-by-tool percentages are not fabricated when no defensible cross-tab exists.
- Overlap with other CODARIS categories is allowed when a technology genuinely spans layers, but its role is labelled here.
