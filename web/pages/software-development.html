ORIENTATION

Roles and responsibilities.

Developers implement behavior; reviewers assess correctness and scope; maintainers preserve understandable interfaces and evidence for future changes.

How the pieces relate

Problem → acceptance criteria → design → implementation
        → review + tests → release → feedback

TECHNICAL GUIDES

Mechanics, tradeoffs and practice.

These are CODARIS editorial explanations. Occupational examples describe engineering responsibilities, not measured demographic shares.

Define observable behavior

Technical model

A requirement should say what a user or caller can observe, under which conditions, and what happens when the operation cannot complete. Constraints such as latency, privacy and accessibility belong beside functional behavior.

Failure modes and decisions

Ambiguous words such as fast or secure do not define acceptance criteria. Separate confirmed requirements from assumptions so a reviewer can challenge the right decision.

Practice task

Turn “members can save articles” into acceptance cases for a valid URL, an invalid URL, an existing article and an unavailable datastore.

Given an authenticated member and a valid article URL
When the member submits the URL
Then exactly one saved item is created
And retrying the same request does not create another item

Model state and invariants

Technical model

Identify the states an entity can occupy and the transitions that are valid. An invariant is a condition that must remain true across operations. Place durable invariants in the datastore when its constraints can express them.

Failure modes and decisions

UI validation is only one input path. Background jobs, migrations and concurrent requests must obey the same rules. Avoid scattering different definitions of a valid state across layers.

Practice task

Model a saved item as active or archived. Specify whether re-adding an archived item restores it or creates a new record.

State: active → archived
Invariant: one item per member + normalized URL
Decision: re-add restores the existing archived item

https://www.postgresql.org/docs/current/ddl-constraints.html ↗

Design interfaces and failure results

Technical model

An interface defines accepted inputs, ownership, results and failure behavior. A caller needs to know whether failure means nothing happened or whether the outcome is uncertain. Explicit contracts reduce accidental coupling.

Failure modes and decisions

Avoid returning a generic success value after ignoring a failed dependency. In C, document who owns returned memory and how partial initialization is cleaned up.

Practice task

Design an add-item operation with separate invalid-input, conflict and storage-failure outcomes. Explain which outcomes can be retried safely.

enum SaveResult { SAVE_OK, SAVE_INVALID, SAVE_EXISTS, SAVE_STORAGE_ERROR };

https://www.gnu.org/prep/standards/html_node/Writing-C.html ↗

Implement a reviewable change

Technical model

A focused change connects one requirement to a limited set of edits. Keep naming, data flow and error paths clear enough that another developer can understand the behavior without replaying your editing session.

Failure modes and decisions

Unrelated refactoring makes a behavioral change harder to review and revert. Small changes still need complete handling of the relevant edge cases; size alone is not quality.

Practice task

Split a feature and a broad formatting cleanup into separate review units, then write an outcome-focused description for the feature.

Review note:
Problem: retries could create duplicate saved items.
Change: enforce uniqueness and return the existing item.
Validation: concurrent retry test and invalid-input cases.

https://google.github.io/eng-practices/review/developer/small-cls.html ↗

Verify at the right boundaries

Technical model

Choose tests that challenge the behavior and its integration points. Pure logic can be tested in isolation; database constraints and transactions need realistic integration checks; user workflows need observable UI outcomes.

Failure modes and decisions

A passing test proves only the cases and assertions it actually exercised. Avoid broad claims from a test that mocks the risky boundary or mirrors the implementation.

Practice task

For each acceptance case, name the cheapest test that provides convincing evidence and one failure it would miss.

Case                         Evidence
Malformed URL                focused validator test
Concurrent duplicate save    database integration test
Error presented accessibly   keyboard + browser check

https://google.github.io/eng-practices/review/reviewer/looking-for.html ↗

Release and maintain

Technical model

A release should identify the exact artifact, configuration and migration assumptions. Maintenance includes adapting behavior, addressing defects and retiring obsolete paths while preserving the ability to understand earlier decisions.

Failure modes and decisions

A source rollback may not restore data compatibility. Record known limitations and recovery steps, and keep diagnostic information useful without logging secrets or unnecessary personal data.

Practice task

Write a release note and rollback plan for the reading-list feature, including the impact of a schema change.

Release evidence: revision + artifact checksum + checks
Rollback condition: sustained save failures
Data requirement: previous binary can read the new schema

https://sre.google/sre-book/release-engineering/ ↗

APPLY WHAT YOU LEARN

Build and verify.

Build a reading-list feature with add, list and archive operations. Deliver a short requirement note, interface description, implementation, focused tests and release note. Include invalid input, duplicate submission, storage failure and recovery behavior.

Evidence to bring to a review

  • A precise description of the behavior and its boundaries.
  • Tests or observations covering success, invalid input and dependency failure.
  • A short explanation of one tradeoff and a known limitation.
  • Instructions that let another developer reproduce the result.

Examples illustrate individual ideas and are not a complete production application. Run experiments in a disposable environment and adapt them to the documented versions of your tools.
