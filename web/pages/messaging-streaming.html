Messaging, Queues & Event Streaming.

Messaging separates the time and location of producing work from consuming it. Queues, retained event logs, publish/subscribe brokers and stream processors solve different coordination problems. Start by specifying delivery, ordering, retention and recovery semantics.

TECHNICAL GUIDES

Mechanics, tradeoffs and practice.

These are CODARIS editorial explanations. Occupational examples describe engineering responsibilities, not measured demographic shares.

Queue versus retained event log

Technical model

A queue commonly distributes work among consumers; a retained log preserves records for consumers to read using positions or offsets. Publish/subscribe distributes events to interested subscribers. Products may support several of these models.

Failure modes and decisions

Do not assume every consumer sees every message or that processed data remains available for replay. Specify retention, subscription behavior and what happens when no consumer is connected.

Practice task

Compare a job-dispatch system with an audit-event stream and explain why their retention and consumer models differ.

https://kafka.apache.org/41/design/design/ ↗

Acknowledgement and duplicate delivery

Technical model

Acknowledgement tells the transport that work has reached a particular point. A consumer can perform an external effect and crash before acknowledging, causing redelivery. Delivery semantics must be considered together with the effect being performed.

Failure modes and decisions

Exactly-once claims are scoped to particular transactions and systems. Use stable identifiers and idempotent handlers when a message can be delivered more than once.

Practice task

Design an email-job handler that records completion and explain the remaining failure window between recording and sending.

https://www.rabbitmq.com/docs/confirms ↗

Ordering and partitions

Technical model

Partitioning distributes storage and processing while defining an ordering domain. A system can preserve order within one partition without providing a global order across all events. Consumer parallelism follows those boundaries.

Failure modes and decisions

A poor partition key can create a hot partition; changing the key can change ordering guarantees. Decide which events actually require relative order.

Practice task

Choose a partition key for account activity and explain how one unusually active account affects capacity.

https://kafka.apache.org/41/getting-started/introduction/ ↗

Retries, poison messages and dead letters

Technical model

A retry policy determines how transient failures are retried and when processing stops. Backoff reduces repeated pressure; dead-letter handling isolates records that cannot be processed normally. Neither mechanism fixes a broken payload by itself.

Failure modes and decisions

Unbounded retries can block progress and hide poison messages. Preserve enough context for investigation, control replay permissions and prevent repeated side effects during recovery.

Practice task

Define a maximum retry policy and an operator workflow for correcting and replaying a malformed event.

https://www.rabbitmq.com/docs/dlx ↗

Backpressure, lag and overload

Technical model

When production outpaces consumption, backlog grows. Lag measures some distance between available and processed work; its meaning depends on whether it counts messages, bytes, offsets or time. Capacity planning needs that distinction.

Failure modes and decisions

Autoscaling consumers may overload the database they call. Bound concurrency and measure downstream saturation rather than treating low queue depth as the only objective.

Practice task

Model a ten-minute producer burst and estimate recovery time when consumers have limited spare capacity.

https://docs.nats.io/nats-concepts/jetstream/consumers ↗

Outbox patterns and schema evolution

Technical model

An application may need to persist data and publish an event about it. An outbox records publication intent in the same database transaction, then a separate process forwards it. Events also need compatible schemas for independent consumers.

Failure modes and decisions

A publisher can still send duplicates, so consumers need idempotency. Avoid changing field meaning silently; plan how old events and older consumers coexist with new versions.

Practice task

Design an order-created event and an outbox row. Identify the transaction boundary and the key used to deduplicate consumption.

https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html ↗
