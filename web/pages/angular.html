TECHNICAL GUIDES

Mechanics, tradeoffs and practice.

These are CODARIS editorial explanations. Occupational examples describe engineering responsibilities, not measured demographic shares.

Components and template boundaries

Technical model

A component combines a class with a template and metadata. Inputs describe data supplied by a parent; outputs communicate events. Keep the component’s responsibility small enough that its state transitions are understandable.

Failure modes and decisions

Avoid reaching into unrelated components to mutate their state. A template should not become a hidden application service or depend on expensive computations on every update.

Practice task

Split a topic list into a list component and an item component, then define their data and event contracts.

import {Component} from "@angular/core";

@Component({
  selector: "app-topic-title",
  template: "<h2>{{ title }}</h2>"
})
export class TopicTitle {
  title = "Developer topics";
}

Signals and derived state

Technical model

Signals track values consumed by the interface. A computed value expresses a derivation from other state, while effects are for interactions that cannot be represented as a pure derivation. Keep the source of truth explicit.

Failure modes and decisions

Duplicating derived values into separately mutable state creates synchronization work. Avoid using effects merely to copy one value into another when a computed relationship is sufficient.

Practice task

Represent a list of topics and a derived count of completed topics without manually updating two counters.

import {signal, computed} from "@angular/core";
const completed = signal([false, true, false]);
const count = computed(() => completed().filter(Boolean).length);

Reactive forms and validation feedback

Technical model

Reactive forms model controls and validation state explicitly. Labels, error descriptions and submit states should make the same workflow usable with keyboard and assistive technology. Browser validation is feedback, not server authorization.

Failure modes and decisions

Show errors at a useful time and preserve input after failure. A disabled submit button alone does not explain what the user needs to fix.

Practice task

Build an email form with required and email validation, an inline error and a server-failure state that preserves the entered value.

import {FormControl, Validators} from "@angular/forms";
const email = new FormControl("", {
  nonNullable: true,
  validators: [Validators.required, Validators.email]
});

Dependency injection and service design

Technical model

Dependency injection supplies collaborators through a declared mechanism rather than hard-coding their creation everywhere. Services can encapsulate data access or shared behavior, but should still have explicit responsibilities and ownership.

Failure modes and decisions

A single global service containing every mutable value creates coupling. Choose provider scope deliberately and keep transport details separate from presentation decisions.

Practice task

Define a topic-reading service interface and describe what the component sees during loading, success and failure.

Component → TopicService → HTTP endpoint
Component state: idle | loading | ready | failed
Transport error → user-facing state, not an unhandled exception

Routing and asynchronous navigation

Technical model

Routing maps URLs to application views and supports navigation state. Data loading and authorization can involve asynchronous operations; the interface needs an intentional experience while those operations are pending or fail.

Failure modes and decisions

A client route guard does not secure server data. The server must independently authorize every protected operation. Preserve useful URLs and avoid losing user work on accidental navigation.

Practice task

Design a detail route with loading, not-found and forbidden states. Explain which decisions belong to the server.

/topics                 → catalogue
/topics/:slug           → topic detail
Unknown slug            → not-found view
Protected API response  → server-enforced authorization

Testing component behavior

Technical model

Component tests should verify rendered behavior and interactions; integration tests should exercise routing and service boundaries where those are the risk. Use semantic queries and test the keyboard path as well as pointer clicks.

Failure modes and decisions

Tests tightly coupled to private component methods can pass while the interface is broken. Cover asynchronous completion and failure rather than only initial rendering.

Practice task

Test that a form error is associated with its input and that a successful topic selection updates the displayed content.

Arrange: service returns a failed request
Act: user submits the form
Assert: inline error is visible, input is retained, retry is possible

APPLY WHAT YOU LEARN

Build and verify.

Build an accessible topic browser with components, a reactive form and loading, empty and failure states. Add tests for keyboard navigation, validation and a failed data request.

Evidence to bring to a review

  • A precise description of the behavior and its boundaries.
  • Tests or observations covering success, invalid input and dependency failure.
  • A short explanation of one tradeoff and a known limitation.
  • Instructions that let another developer reproduce the result.

Examples illustrate individual ideas and are not a complete production application. Run experiments in a disposable environment and adapt them to the documented versions of your tools.
