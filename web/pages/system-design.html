TECHNICAL GUIDES

Mechanics, tradeoffs and practice.

These are CODARIS editorial explanations. Occupational examples describe engineering responsibilities, not measured demographic shares.

Requirements and workload estimates

Technical model

Separate functional requirements from constraints such as latency, availability, retention and data size. Estimate traffic and storage using explicit assumptions, then identify which assumptions dominate the design.

Failure modes and decisions

Average traffic can hide bursts and uneven tenants. Avoid pretending estimates are measurements; record uncertainty and plan how production observations will refine the model.

Practice task

Estimate requests per second for 100,000 daily submissions concentrated in a two-hour period and compare with a uniform-day estimate.

Uniform: 100000 / 86400 ≈ 1.16 requests/s
Two-hour window: 100000 / 7200 ≈ 13.9 requests/s
Neither estimate includes retries or burst amplification.

State ownership and consistency

Technical model

Identify the authoritative owner of each fact and where derived copies exist. Caches, search indexes and analytics tables may lag behind the source. Operations that span boundaries need an explicit consistency model.

Failure modes and decisions

Two writable copies without a conflict policy create ambiguity. Do not call a workflow atomic if part of it happens later in another system.

Practice task

Assign ownership for application status and notification state, then explain what the UI shows before a notification is delivered.

Authoritative: application.status
Derived: search index, dashboard counters
Asynchronous: notification delivery status

Caching and invalidation

Technical model

A cache trades freshness and operational complexity for lower latency or reduced load. Define keys, expiration, invalidation triggers and cache-miss behavior before introducing one. Private and public data need different isolation rules.

Failure modes and decisions

A cache can amplify failures through synchronized expiry or repeated misses. Bound fallback load and ensure one user cannot receive another user’s cached response.

Practice task

Design a cache for public topic metadata and explain why member-specific application details need different keys or no shared cache.

Cache key: topic ID + content version
Cache miss: bounded fetch from origin
Private account data: separate authorization-aware policy

Queues and asynchronous workflows

Technical model

A queue decouples request completion from later work. It introduces states such as accepted, processing, completed and failed. Users need to understand which state a successful API response actually confirms.

Failure modes and decisions

A worker can crash after performing an effect but before acknowledgement. Use idempotent operations and record enough state to reconcile uncertain outcomes.

Practice task

Design notification processing so a retry does not generate uncontrolled duplicate messages.

Accepted ≠ completed
Submission transaction → outbox row
Publisher → queue → idempotent consumer → delivery result

Overload and partial failure

Technical model

Dependencies can become slow without fully failing. Deadlines, concurrency limits and bounded queues keep that slowness from consuming every resource. Load shedding preserves useful service when demand exceeds capacity.

Failure modes and decisions

Retries multiply load during an outage. Coordinate retry budgets and stop accepting work that cannot complete within its useful deadline.

Practice task

Describe what your service does when the database is slow for five minutes, including user feedback and queued work.

Request budget: 2 s
Database budget: 1 s
Queue: bounded
Over capacity: explicit retryable response, not unlimited waiting

https://sre.google/sre-book/handling-overload/ ↗

Recovery and design validation

Technical model

A design is incomplete without evidence that state and service can be recovered. Define recovery point and time objectives, backup ownership, restore checks and compatibility requirements. Rehearse failures in a controlled environment.

Failure modes and decisions

Replication can copy an accidental deletion. A backup that has never been restored is an untested recovery assumption. Include configuration and secrets access in the restoration plan.

Practice task

Run a tabletop exercise: the primary database is unavailable and the latest deployment contains a bug. Decide the recovery order.

Recovery checklist:
1. Identify trusted backup and target revision.
2. Restore to an isolated environment.
3. Validate invariants and sample workflows.
4. Redirect traffic with rollback criteria.

https://sre.google/sre-book/data-integrity/ ↗

APPLY WHAT YOU LEARN

Build and verify.

Design an application-review service. Include submission, review, notification and audit history. Produce a component diagram, data model, capacity estimate, failure table and recovery procedure.

Evidence to bring to a review

  • A precise description of the behavior and its boundaries.
  • Tests or observations covering success, invalid input and dependency failure.
  • A short explanation of one tradeoff and a known limitation.
  • Instructions that let another developer reproduce the result.

Examples illustrate individual ideas and are not a complete production application. Run experiments in a disposable environment and adapt them to the documented versions of your tools.
