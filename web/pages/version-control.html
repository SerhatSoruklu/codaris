Version Control & Code Hosting.

Version control records changes and relationships between revisions. Hosting services add collaboration, review and automation around that history. A sound workflow makes it possible to explain, review and recover a change.

ORIENTATION

Roles and responsibilities.

Developers prepare focused commits; reviewers evaluate intent and evidence; maintainers protect release history and repository permissions.

How the pieces relate

Working tree → staging area → local commit graph
                              ↔ remote repository → review → integration

TECHNICAL GUIDES

Mechanics, tradeoffs and practice.

These are CODARIS editorial explanations. Occupational examples describe engineering responsibilities, not measured demographic shares.

Working tree, index and commit

Technical model

In Git, edited files, staged content and committed snapshots are separate states. A commit records staged content, not every working-tree edit. Understanding those states prevents accidental omissions and unrelated changes in a review.

Failure modes and decisions

Inspect both staged and unstaged diffs before committing. Untracked files and generated artifacts need deliberate inclusion or exclusion. A clean working tree says nothing about whether the code is correct.

Practice task

Stage only one logical change, inspect the staged diff and explain what remains uncommitted.

https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository ↗

Branches, merges and conflict resolution

Technical model

A branch names a position in a commit graph. Integration combines histories or replays changes; conflicts identify places where automatic combination is insufficient. Resolution needs an understanding of both intended behaviors.

Failure modes and decisions

A conflict-free merge can still be semantically wrong. Build and test the combined behavior, especially when one change alters an interface used by another.

Practice task

Create two changes to the same function in a scratch repository, resolve the conflict and test both requirements.

https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging ↗

Code hosting and review policy

Technical model

A forge provides pull requests, issues, permission models and integration controls. Those policies belong to the hosting service; local Git alone does not enforce reviewer approval or required checks.

Failure modes and decisions

Review the final diff and required checks against the branch being merged. Protect privileged automation from untrusted contributions and avoid assuming all repository collaborators need administration rights.

Practice task

Design a small-team review policy with required checks, reviewer ownership and an emergency-change process.

https://docs.github.com/en/pull-requests/collaborating-with-pull-requests ↗

Reverting and recovering

Technical model

Reverting adds a change that undoes earlier behavior without deleting history. Rewriting history changes commit identity and affects collaborators. Recovery should start by identifying the desired resulting tree and the scope of published work.

Failure modes and decisions

Avoid rewriting shared history casually. Preserve a recoverable reference before complex operations and distinguish source rollback from database or deployment rollback.

Practice task

In a scratch repository, revert a faulty commit and verify that an unrelated later fix is retained.

https://git-scm.com/docs/git-revert ↗

Large files and non-source artifacts

Technical model

Binary assets, generated outputs and datasets have different review and storage characteristics from source text. Specialized large-file or data-versioning tools can keep references to content outside the main repository history.

Failure modes and decisions

External object storage must be backed up and accessible to reproducible builds. A pointer in Git is not the data itself; avoid committing credentials or private datasets as ordinary artifacts.

Practice task

Document which artifacts belong in source control and how a clean checkout obtains every required external object.

https://git-lfs.com/ ↗

Useful commits and provenance

Technical model

A focused commit explains one change with enough context to understand why it exists. Tags and release records connect source revisions to shipped artifacts. Provenance improves traceability but does not replace correctness review.

Failure modes and decisions

Huge unrelated changes are hard to review and hard to revert. Avoid messages that describe only editing actions instead of the resulting behavior.

Practice task

Split an imagined bug fix and formatting cleanup into separate commits; write an outcome-based description and validation note for each.

https://git-scm.com/book/en/v2/Distributed-Git-Contributing-to-a-Project ↗
